# 1. 系统架构与数据流

## 1.1 架构总览

## 1.2 组件职责与交互逻辑

### 1.2.1 边缘层

| 组件 | 职责 | 关键设计 |
|---|---|---|
| CDN | 分发视频分片、静态资源、封面图 | 分片走 CDN 回源，源站只做鉴权；未签名请求一律 403 |
| WAF | 拦截 OWASP Top 10、恶意爬虫 | 规则与业务限流分离，避免误伤正常上传 |
| Nginx | TLS 终止、路由、限流 | 大文件上传**旁路**：客户端直传对象存储，Nginx 不代理字节流 |

**关键决策：上传旁路（Presigned Direct Upload）**
视频动辄数 GB，若经应用服务器中转，会同时吃掉入口带宽、应用内存与连接数。因此流程改为：

```
Client ──1. 申请上传凭证──▶ Content Svc ──2. 校验配额/频率──▶ 返回 presigned PUT URL
Client ──3. 直传对象存储──────────────────────────────────▶ S3/OSS（字节流不经过应用）
Client ──4. 回调 upload-complete──▶ Content Svc ──5. 投递 MQ──▶ 转码 + 预审
```

应用层只处理"凭证签发"和"完成回调"，两者都是轻量 JSON 请求。

### 1.2.2 应用层（8 个服务）

采用**模块化单体起步、按压力拆分微服务**的策略。初期 8 个服务作为同一 NestJS 应用内的模块部署，代码边界严格；当某模块 QPS 或资源画像显著偏离时，直接抽出为独立进程——因为模块间只通过接口与 MQ 通信，抽离不需要重写业务逻辑。

| 服务 | 职责 | 数据依赖 |
|---|---|---|
| Auth Service | 注册、登录、2FA、令牌签发与吊销、RBAC 判定 | PG(users), Redis(session) |
| User Service | 资料、配额、封禁、GDPR 导出/删除 | PG, MongoDB |
| Content Svc | 上传凭证、内容元数据、分类标签、检索 | PG, MongoDB |
| Media Svc | 转码编排、HLS/DASH 清单、签名 URL 签发 | S3, PG |
| Audit Svc | 预审结果聚合、人工复审队列、申诉、审核日志 | PG, MongoDB |
| Playback Svc | 播放鉴权、分片地址下发、播放进度 | Redis, PG |
| Comment Svc | 弹幕、评论、点赞 | MongoDB(弹幕), PG |
| Download Svc | 下载鉴权、次数/带宽配额、签名 URL | PG, Redis |

### 1.2.3 数据层的分工原则

三类存储各司其职，**不做冗余写入**（同一份数据只有一个权威源）：

| 存储 | 权威数据 | 为什么 |
|---|---|---|
| PostgreSQL | 用户、角色权限、内容主记录、审核日志、订单式配额 | 需要强事务与外键约束；审核状态流转必须 ACID |
| Redis | 会话、令牌黑名单、限流计数、热点内容缓存、播放进度 | 高频读写、可丢失、TTL 天然契合 |
| MongoDB | 弹幕、逐帧时间戳注释、多语言字幕、非结构化元数据扩展 | 写多读多、schema 灵活、单文档自包含 |
| 对象存储 | 源文件、转码产物、截图、文档附件 | 大二进制、需 CDN 回源 |

> **一致性说明**：内容主记录在 PG，MongoDB 中仅存 PG 主键的引用与扩展字段。删除内容时先软删 PG，再由 MQ 异步清理 MongoDB 与对象存储，保证最终一致。

### 1.2.4 消息队列的 Topic 设计

| Topic / Queue | 生产者 | 消费者 | 幂等键 | 死信策略 |
|---|---|---|---|---|
| `content.uploaded` | Content Svc | Transcode Wkr, AI Audit Wkr | `contentId` | 3 次重试 → DLQ |
| `media.transcoded` | Transcode Wkr | Content Svc, Notify Wkr | `contentId:profile` | 3 次 → DLQ |
| `audit.precheck.completed` | AI Audit Wkr | Audit Svc | `contentId:engineVersion` | 5 次 → DLQ + 人工告警 |
| `audit.manual.required` | Audit Svc | 审核工作台（WebSocket 推送） | `contentId` | — |
| `notify.dispatch` | 各服务 | Notify Wkr | `eventId` | 5 次 → DLQ |

**幂等性要求**：所有消费者必须实现幂等。转码任务用 `contentId + profile` 做 Redis SETNX 锁；审核结果写入用 `UPDATE ... WHERE status = 'pending_precheck'` 的条件更新保证重复消费不产生二次流转。

## 1.3 核心数据流：上传 → 审核 → 发布

这是全平台最关键的链路，串联所有组件：

```
① 客户端发起上传意图
   POST /api/v1/contents/upload-intent
   └─ Auth: JWT 校验 → RBAC: 上传权限
   └─ Quota: 查 PG 当日配额 + Redis 频率计数
   └─ 返回: presigned URL (有效期 15min) + contentId (status=DRAFT)

② 客户端直传对象存储
   PUT <presigned-url>  ──▶ S3/OSS
   └─ 对象存储侧校验签名、大小上限、Content-Type
   └─ 打上临时标签 quarantine=true

③ 客户端通知完成
   POST /api/v1/contents/{id}/upload-complete
   └─ 应用校验对象是否真实存在（HEAD Object）+ ETag 比对
   └─ status: DRAFT → UPLOADED
   └─ 投递 content.uploaded 到 MQ

④ 两条 Worker 并行消费

   ┌── Transcode Wkr ──────────────────────────────┐
   │  · 探测格式/时长/码率 (ffprobe)                │
   │  · 视频 → 多档 HLS (1080p/720p/480p) + DASH    │
   │  · 音频 → 无损档 + 有损档（见下方说明）         │
   │  · 生成封面、雪碧图、缩略图、波形图             │
   │  · 输出回对象存储，清单文件入库                 │
   │  · status: UPLOADED → TRANSCODING → 产物就绪    │
   │  · 发布 media.transcoded                       │
   └────────────────────────────────────────────────┘

   ┌── AI Audit Wkr ───────────────────────────────┐
   │  · 视频抽帧 → 图像识别 (NSFW/暴恐/涉政)         │
   │  · 音轨 → ASR 转文字 → 关键词/语义过滤          │
   │  · OCR 抽帧文字识别                             │
   │  · 聚合为 riskScore (0-100) 与风险分类          │
   │  · 发布 audit.precheck.completed               │
   └────────────────────────────────────────────────┘

⑤ Audit Svc 依据策略决策（阈值可配）

   riskScore < lowThreshold(30)        → status=AUTO_PUBLISHED（直接发布）
   lowThreshold ≤ riskScore < high(70) → status=PENDING_MANUAL（进入人工队列）
   riskScore ≥ highThreshold(70)       → status=BLOCKED（自动拦截 + 通知用户 + 开放申诉）

   注：AUTO_PUBLISHED 与下文人工通过的 PUBLISHED 是对外可见性完全相同的两个终态，
   区别仅在于"放行决策由系统还是由人做出"，用于误杀率回溯。判定可见性时必须
   使用 status IN ('PUBLISHED','AUTO_PUBLISHED')，不能只判 PUBLISHED。

⑥ 人工复审（工作台）
   · 审核员领取任务（乐观锁防重复领取；15 分钟未决策自动释放）
   · 通过 → PUBLISHED；驳回 → REJECTED（附驳回理由）
   · 严重违规 → 直接 BLOCKED（跳过 REJECTED，保留申诉入口）
   · 封禁账号（需 user:ban 权限）
   · 全过程写入 audit_logs（不可篡改，仅追加）

⑦ 发布后可播放
   · Playback Svc 签发分片级短期签名 URL
   · CDN 回源时校验签名 → 命中则返回分片
```

### 1.3.1 音频内容的转码策略（无损音质要求）

音频内容与视频的关键差异：需求要求**支持无损音质播放**，因此不能像视频那样"一律转成有损多档"。

| 产物档位 | 格式 | 用途 | 生成条件 |
|---|---|---|---|
| **原始档（无损保留）** | 保持源格式（FLAC / ALAC / WAV / APE） | "无损下载"与高保真播放 | 源本身是无损格式时，**原样保留**，绝不重编码 |
| **无损转封装** | FLAC（若源为 WAV/APE 等不便流式播放的格式） | 流式播放 + 无损下载 | 源无损但容器不适合渐进式传输时，无损转封装（不损失信息） |
| **有损高档** | AAC 256 kbps / Opus 192 kbps | 移动网络、后台播放省流 | 始终生成 |
| **有损低档** | AAC 96 kbps | 弱网降级 | 始终生成 |

**核心原则**：
1. **无损源绝不重编码为有损后再当"无损"**。若用户上传 FLAC，系统保留原始对象，`assetKind: 'SOURCE'` 指向它。任何声称"无损"的产物必须是原始文件或无损转封装结果。
2. **有损档始终额外生成**，因为移动网络下播放无损 FLAC（约 900 kbps）体验很差，自适应码率需要降级选项。
3. **播放链路按网络自适应**：默认走 AAC 256 kbps，用户可在播放器中显式选择"无损"，此时切换到 FLAC 流。UI 上明确标注当前码率与"无损"标识，避免用户误以为一直在听无损。
4. **雪花图 → 波形图**：音频内容生成波形图（waveform）用于播放器进度条与频谱可视化的静态预览，而非视频的雪碧图缩略帧。

> **关于"后台持续播放"的架构前提**：无损 FLAC 的带宽成本是有损的 3–4 倍，若大量用户以无损档后台长时间播放，出口带宽压力显著。因此后台播放与弱网场景下，即使用户选择了"无损"，也建议降级到有损档并在恢复前台时切回——此策略可配置，默认开启。

### 1.3.2 审核状态机

```
                        ┌─────────┐
                        │  DRAFT  │  创建上传意图，尚未上传完成
                        └────┬────┘
                             │ upload-complete（服务端校验对象真实性）
                        ┌────▼─────┐
                        │ UPLOADED │
                        └────┬─────┘
                             │ MQ: content.uploaded
                             │ 转码与预审并行消费同一条消息
                             │ status 由先完成者推进，后完成者只更新自己的产物字段
                ┌────────────┴────────────┐
                │                         │
                │ 转码失败                  │ 预审完成
        ┌───────▼────────┐        ┌───────▼────────┐
        │TRANSCODE_FAILED│        │  PRECHECK_DONE │
        └───────┬────────┘        └───────┬────────┘

                │            ┌────────────┼────────────┐

                │                         │                  │
                │                  ┌──────▼──────┐    ┌──────▼──────┐
                │                  │  人工复审    │    │  APPEALING  │
                │                  └──┬───────┬──┘    └──────┬──────┘
                │                     │       │              │
                │         ┌───────────▼─┐  ┌──▼────────┐  ┌──▼───────────┐

                │         │  已对外可见  │  └─────┬─────┘  └──┬────────┬──┘
                │         └─────────────┘        │           │        │
                │                                │  ┌────────▼──┐  ┌──▼────────┐
                │                                │  │ PUBLISHED │  │ REJECTED  │
                │                                │  │ (申诉通过) │  │ (申诉驳回) │
                │                                │  └───────────┘  └───────────┘
                │                                │
                └────────────────────────────────┴──────▶ 归档（终态）

    注：所有状态均可软删至 DELETED（图中省略，详见 03 节 STATE_MACHINE）
        PENDING_MANUAL 亦可由审核员直接判定严重违规 → BLOCKED
```

> **与 03 节 STATE_MACHINE 的关系**：上面这张图是**帮助读者建立整体认知的示意图**，为可读性省略了运维与异常分支。03 节的 `STATE_MACHINE` 表才是**代码层的权威约束**，它额外包含 `TRANSCODE_FAILED → REJECTED`（转码彻底失败归档）与各状态到 `DELETED` 的软删路径。两者冲突时以 03 节的表为准。

**两个必须明确的语义**：

1. **`AUTO_PUBLISHED` 与 `PUBLISHED` 都是"已发布"终态，不是前后关系。** 前者表示系统自动放行，后者表示人工放行。二者对用户的可见性完全一致。所有查询可见内容的 SQL **必须**写作 `status IN ('PUBLISHED','AUTO_PUBLISHED')`——写成 `= 'PUBLISHED'` 会导致自动放行的内容在列表、播放、下载三处全部不可见。

2. **`TRANSCODING` 不是预审的前置条件。** 转码与预审是并行消费同一条 `content.uploaded` 消息的两个独立 Worker。预审的准入条件是 `status IN ('UPLOADED','TRANSCODING')`，而非等待转码完成——否则预审会被转码时长（数分钟到数十分钟）阻塞，人工队列积压。风险是预审可能在转码尚未产出预览时完成，此时审核员看到的是原始文件预览而非转码产物，这是可接受的（预览走低码率即时转码）。

**状态流转的强约束**：所有状态变更必须通过 `Audit Svc` 的单一入口 —— 即 `applyTransition()`（其内部调用 `transitionStatus()` 完成实际的锁定、校验与日志写入）。禁止其他服务直接 UPDATE `status` 字段。该入口内部用行级锁 + 条件更新，并在同一事务内写入 `audit_logs`，保证"状态变了但没日志"不可能发生；非法跃迁的审计记录则由 `applyTransition` 在业务事务回滚后用独立事务写入（详见 03 节 3.4.5）。

> **实现注意**：`transitionStatus()` 内部必须**重新读取当前状态**作为 `from`，不能使用调用方传入的、可能已过期的对象快照。否则在"申诉中→已通过"这类二次流转中，条件更新 `WHERE status = <陈旧值>` 将永远匹配不到行，导致流转静默失败。

## 1.4 防误杀策略的架构落点

误杀是审核系统的核心体验风险。架构上提供四层缓冲：

| 层 | 机制 | 落点 |
|---|---|---|
| 1. 阈值可配 | `riskScore` 分段阈值存于配置中心，支持按内容类别差异化配置 | Audit Svc 策略引擎 |
| 2. 分档而非二分 | 高风险才自动拦截；中风险进人工；低风险直接放行 | 状态机三分支 |
| 3. 申诉通道 | BLOCKED / REJECTED 均可申诉，申诉走独立队列，优先级高于新内容 | 申诉表 + 独立队列 |
| 4. 灰度发布 | 新模型/新阈值先对 5% 流量生效，观察误杀率再全量 | 策略引擎的 `rolloutPercent` |

**关键指标**：所有审核决策写入日志后，需持续监控 **误杀率 = 申诉成功数 / 拦截总数**。若该指标超过 5%，自动告警并建议回滚阈值。

## 1.5 水平扩展能力设计

| 层 | 扩展方式 | 瓶颈与对策 |
|---|---|---|
| 接入层 | Nginx 增加实例 + 上层 LB | 无状态，直接加 |
| 应用层 | 无状态 Pod 水平扩容 | 会话在 Redis，无本地状态；HPA 按 CPU + 队列深度 |
| Worker 层 | 按队列积压扩容 | Kafka 分区数决定并行上限；转码 Worker 独立节点池（吃 CPU） |
| PostgreSQL | 读写分离 + 分区 | 读走从库；`audit_logs`、`play_events` 按月分区；写瓶颈则按 `userId` 分片 |
| Redis | Cluster 分片 | 会话与限流 key 天然可分片 |
| MongoDB | 分片集群 | 按 `contentId` 哈希分片 |
| 对象存储 | 天然无限扩展 | 仅需注意 CDN 回源带宽 |
| MQ | 增加分区与消费者 | 分区数是并行度上限，初期预留 24 分区 |

**扩容触发信号**：
- 应用层：P99 延迟 > 300ms 或 CPU > 70% 持续 5 分钟
- Worker 层：`audit.precheck.queue` 积压 > 1000 或最老消息滞留 > 10 分钟
- 数据库：从库复制延迟 > 5s 或连接池等待 > 20%

## 1.6 多活与容灾

- **对象存储**：开启跨区域复制，主区故障时 CDN 切备区
- **PostgreSQL**：同步流复制到同城备库，异地异步；RPO < 5s，RTO < 2min
- **Redis**：主从 + Sentinel，会话可重建（用户重新登录），不追求零丢失
- **MQ**：三副本，`min.insync.replicas=2`
- **降级预案**：AI 审核引擎不可用时，**默认策略是全部转人工队列**而非直接放行——安全兜底优先于可用性
